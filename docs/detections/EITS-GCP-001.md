# EITS-GCP-001: New service-account key used to set a project IAM policy

The design requires a successful `iam.googleapis.com` / `google.iam.admin.v1.CreateServiceAccountKey` record with `protoPayload.response.name`, followed within 30 minutes by successful `cloudresourcemanager.googleapis.com` / `SetIamPolicy` in the same **log-owning project**. The second record must carry `protoPayload.authenticationInfo.serviceAccountKeyName` matching that exact resource path after removal of the documented `//iam.googleapis.com/` prefix. Both timestamps must be present and strictly ordered. Evidence is the two original records.

Public field definitions: [AuditLog and authentication information](https://docs.cloud.google.com/logging/docs/reference/audit/auditlog/rest/Shared.Types/AuditLog), [service-account key resource](https://docs.cloud.google.com/iam/docs/reference/rest/v1/projects.serviceAccounts.keys), [IAM audit method names](https://docs.cloud.google.com/iam/docs/audit-logging), and [Resource Manager audit methods](https://docs.cloud.google.com/resource-manager/docs/audit-logging). The [service-account audit examples](https://docs.cloud.google.com/iam/docs/audit-logging/examples-service-accounts) document the key-use field and warn that some services omit it; creation examples do **not** guarantee `response.name` is logged. This rule is conditional on its presence.

A newly created persistent credential immediately making an access-control change is worth investigating. Routine bootstrap, deployment, and credential rotation can produce the same sequence, including removing access. The rule does not infer a new privilege grant from an API method name. Inspect the retained request, response and any policy delta before assessing the actual change.

Observed facts are the logged successful creation, reported key resource name, subsequent policy-setting API, same project scope and elapsed time. The inference is possible credential misuse or unauthorized access-control modification. Malicious intent, authorization, key theft, effective permissions, whether the policy changed, persistence and the identity of the human operator remain unresolved. ATT&CK T1098.001 describes the credential-persistence hypothesis; it is not a verdict.

The executable logic is [SQL](../../src/eits/sql/EITS-GCP-001.sql); [metadata](../../src/eits/rules/gcp.json) contains evidence fields and required telemetry. Success requires explicit numeric `status.code=0` or an explicitly empty status object; omitted/null status stays unknown. Keys with alternate email/numeric-ID/wildcard spellings are not resolved as aliases. Missing creation responses, missing key-use attribution, delayed use, cross-project use and other API methods are blind spots. Equal timestamps do not establish ordering. A 30-minute upper boundary is inclusive.

Tuning should inspect the concrete key, project, caller, policy target and approved change history. Any future exception should be narrow, dated and measured against missing attacks. No allowlist or candidate revision is shipped. The corpus deliberately retains authorized rotation false positives, delayed-use false negatives, ambiguous alerts, absent-attribution false negatives and boundary cases. [Ground truth](../../evaluation/gcp-ground-truth.json) is separate from parser input.
